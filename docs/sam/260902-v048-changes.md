## 二、maki jobs API 用法

Neovim `vim.fn` 风格的后台进程控制,挂 `maki.fn` 下,需插件 `run` 权限。文档源:`site/docs/content/lua-api/_index.md` 的 `maki.fn` 一节(由 `just gen-docs` 生成),实现:`maki-lua/src/api/fn.rs`。

### 1. API 一览

| 函数 | 作用 |
|---|---|
| `jobstart(cmd, opts)` | 启动后台命令,返回 job id |
| `jobstop(id)` | SIGKILL 杀掉 |
| `jobwait(id, timeout_ms?)` | 等待完成并收集输出(默认 30s) |
| `jobinfo(id)` | 快照:id、command、pid、status、exit_code、tail 行 |
| `joblist(session?)` | 列出可见任务(可过滤 session) |
| `jobfind(name)` | 按名字找**存活**任务 |
| `jobattach(id, opts)` | reload 后重挂回调 |
| `jobforget(id)` | 丢弃已退出的 session 任务 |

### 2. jobstart 参数

```lua
local id = maki.fn.jobstart(cmd, {
  cwd = "~/projects",
  env = { VAR = "value" },
  on_stdout = function(_, line) end,  -- (job_id, line)
  on_stderr = function(_, line) end,
  on_exit   = function(_, code) end,
  stdout = "/path", stderr = "/path",  -- 重定向文件(需 fs_write,与回调互斥)
  scope = "task" | "plugin" | { session = "<id>" },
  tail = 20,       -- jobinfo 保留尾部行数(0 禁用,最大 1024)
  name = "my-job", -- jobfind 句柄,同名存活任务报错
})
```

- **cmd 形态**:字符串 → `bash -c`(Unix)/ `cmd /C`(Win);表 → argv 直接派生子进程,无 shell(重定向/管道/`$()` 均不生效)。
- **scope**:
  - `"task"`(默认):本轮调用结束即终止
  - `"plugin"`:活到插件卸载/重载
  - `{ session = id }`:活到 session 结束,**跨插件 reload 存活**(进程继续,仅 Lua 回调被卸载)

### 3. 典型模式

```lua
-- 等结果
local result = maki.fn.jobwait(maki.fn.jobstart("echo hello"), 5000)
print(result.stdout)  -- { stdout, stderr, exit_code, truncated }

-- 后台监控,reload 不丢(官方示例)
local sid = maki.session.current()
local id = maki.fn.jobfind("log-tail")
  or maki.fn.jobstart({ "tail", "-F", path }, { name = "log-tail", scope = { session = sid } })
maki.fn.jobattach(id, {
  on_stdout = function(_, line) maki.session.notify(line, { session = sid }) end,
  on_exit = function(_, code) maki.session.notify("tail died: " .. code, { session = sid }) end,
})

-- 只创建不跟进
maki.fn.jobstart("cargo build", {
  stdout = "/tmp/build.log", stderr = "/tmp/build.log",
  on_exit = function(_, code) if code ~= 0 then ... end end,
})
```

### 4. 坑

- `jobwait` 超时返回 `nil`(不是空表)
- `jobfind` 只认活任务;退出后用 `jobfind(...) or jobstart(...)` 重启
- 已退出的 session 任务仍可从快照应答(`truncated` 标记 tail 是否丢行);task/plugin 任务退出即删,再 wait 是错误
- `jobwait` 等待期间 `on_stdout` 等回调照常触发(类 Neovim)
- `jobattach` 挂到已退出任务上会立即触发一次 `on_exit`,避免 reload 竞态丢事件

### 1. 包管理器(maki-pack,内置,无需自写)

"包" = 一个 Git 仓库 = 插件代码 + `plugin.toml` 清单。声明安装(全局 `~/.config/maki/init.lua`):

```lua
maki.pack.add({
  "https://github.com/example/maki-goal",          -- 字符串 = source
  { src = "...", version = "v1.2.0", name = "...", data = {...} },  -- 带版本的表

```

- 启动时终端一次性确认;选中 commit 写入 `pack-lock.json`(提交它使多机一致)
- `confirm = false` 跳过确认(不跳过权限);`load = false` 只装不加载;`load = fn(pkg)` 自定义入口
- 锁文件优先于 `version`;`/packupdate [name]` 升级(老/新 commit + 权限变化审查,`!` 跳过审查,`++lockfile` 恢复锁文件版本);`/packdel [name|++all]` 删除

### 2. 插件编写(四步)

1. 写 `~/.config/maki/lua/<name>.lua`(或项目 `.maki/`),`maki` 全局已就绪:

```lua
maki.api.register_tool({
  name = "hello",
  description = "Say hello to a name.",
  parameters = { type = "object", properties = { name = { type = "string" } }, required = { "name" } },
  handler = function(args)
    return { llm_output = "hello " .. args.name }
  end,
})
```

2. `init.lua` 里 `require("hello")`
3. 同目录 `plugin.toml` 授权(`[permissions]` 各项,缺文件全部拒绝)

### 1. 时间线

### 2. v0.4.8 之前(v0.3.26 起)的用法

1. **开启**:会话内 `/workflow` 切换,或配置 `always_workflow = true` 默认开。
2. **机制**:workflow 模式下 `code_execution`(Python 沙箱)内可调用 `task` 工具及声明了 `workflow` audience 的工具,从脚本编排子代智能体。
3. **写法**(v0.4.8 时代沙箱内):

```python
# 串行
result = await task(description="研究 xxx", prompt="...", subagent_type="research")

# 并行 fan-out
r1, r2 = await asyncio.gather(
    task(description="任务A", prompt="..."),
    task(description="任务B", prompt="..."),
)

# 结构化结果:output_schema 传 JSON Schema,返回 JSON 字符串
res = await task(description="校验", prompt="...", output_schema={...})
import json; data = json.loads(res)
```

4. **关键约束**:必须 `await` 每个 `task(...)`;并行用 `asyncio.gather`;`output_schema` 给结构化 JSON 结果;调大 code_execution 的 `timeout`(子代理存活超过默认沙箱超时);沙箱内"广告即可调"由同一谓词 `interpreter_tools(tools, audience, workflow)` 保证结构性一致。
5. **声明侧**:工具要能在 workflow 中被调,`register_tool` 声明 `audiences = { "main", "workflow" }`(task 插件 `plugins/task/init.lua:258`);沙箱是调用约定而非权限授予,read-only 子代理不会因此获得写工具。

### 3. v0.4.8 → v0.5.0 的差异

仅 `plugins/code_execution/init.lua` 提示语微调:`asyncio.gather` 示例改为 `gather(task(...), task(...))`(v0.5.0 沙箱内工具绑成可直接 `await` 的 async 函数),行为未变。

## 七、子智能体:进程模型、会话查看与 id(追加调查)

> 追加于 2026-09-02 20:47

### 1. 子智能体不是独立进程

`task` 子代理(`maki.agent.session()`)跑在同一个 maki 进程内,是同一 smol 异步 runtime 上的独立 agent 循环,没有 pid/子进程(`maki-lua/src/api/agent.rs`)。

- 独立:自己的对话历史 `History::new(...)`、自己的 MCP session、自己的 cancel trigger、自己的 `RunLedger`(usage 独立统计)
- 共享(agent.rs:599-610):父级 permissions、`file_access` 文件锁、`prompt_slots`、tool registry、model_policy —— 子代理不另起权限审批,两子代理不会互踩文件锁
- 事件经 `smol::spawn(relay_session_events(...))` 转发回父级 UI(agent.rs:557)
- 要真正独立进程须另起 `maki --print`/headless 子进程或外部编排

### 2. 如何查看子智能体会话

- 运行中:主 transcript 直接看到其工具调用流;`/tasks` 打开 task 插件实现的 tasks picker(`plugins/task/picker.lua`),列出当前会话子代理,运行中的排最前,显示 id/name/model/状态,可聚焦查看
- 历史:子代理**不单独持久化为独立 session**;继承父会话 id(agent.rs:596 `session_id: agent_ctx.session_id.clone()`),转写存进父会话存储(`maki-storage/src/sessions.rs`):

```rust
pub struct StoredSubagent {
    pub tool_use_id: String,   // 子代理标识
    pub name: String,
    pub model: Option<String>,
}
// subagent_messages: HashMap<String, Arc<Vec<M>>>  // 按 tool_use_id 存消息
```

查历史 = 查父会话 session 文件里的 `subagent_messages` 段。

### 3. 如何取得其 id

子代理**没有独立 session id**,唯一标识是 `tool_use_id` / `ui_id`(agent.rs:570-573):

```rust
let ui_id = agent_ctx.tool_use_id.clone()
    .unwrap_or_else(|| format!("session-{}", MakiId::generate()));
```

- 模型发起 `task` 调用时 → id = 该工具调用的 `tool_use_id`
- 无工具调用时(workflow 模式 Lua 直接开 session)→ `session-<MakiId>`

插件/脚本中获取:

```lua
local sid = maki.session.current()   -- 父会话 id(子代理内部也是它)
maki.events.on("TaskStatusChanged", function(data)
  print(data.id, data.name, data.status)   -- data.id = tool_use_id
end)
```

`/tasks` 里选中子代理时 `task.id` = 该 `tool_use_id`。

总结:子代理 = 同进程、同 session 下的独立上下文;标识用 `tool_use_id`(非新 session id);查看用 `/tasks` + 主 transcript,历史在父会话文件里。

### 5. workflow 触发方式:如何开、自然语言如何触发

开启方式只有两种(模型无法自己开):

1. 手动:TUI 输入框输入 `/workflow` 回车 → 翻转状态,flash workflow on(`maki-ui/src/app/mod.rs:1414-1425`)
2. 配置:`maki.setup({ always_workflow = true })` → 每会话默认开

代码确认:
- `/workflow` 是纯 UI 命令,只翻转 `state.workflow`,不经模型
- **没有** `set_workflow`/`toggle_workflow` 之类的 agent 工具(全仓库 grep 无结果)
- headless/SDK 的 `HeadlessParams.workflow` 无 CLI flag(`src/cmd/subcmd.rs:703` 硬编码 `false`),只能走 API/SDK

自然语言触发:
- **自然语言不能直接开 workflow**(模型无开关工具);说"开 workflow"它做不到,只能建议你按 `/workflow` 或改配置
- 自然语言触发的是 **workflow 模式下的编排行为**:开启后,用户用自然语言描述并行/编排意图,模型就在 `code_execution` 沙箱里写 Python 调 `task`

示例对话(workflow 已开):

```
你: 用两个子代理并行调研前端最佳实践和后端 API 设计,汇总结果
模型: [调用 code_execution,脚本内]
  r1, r2 = await gather(
      task(description="调研前端", prompt="...", subagent_type="research"),
      task(description="调研后端", prompt="...", subagent_type="research"),
  )
  print(r1); print(r2)
```

注意点:
- workflow **未开**时 `code_execution` 沙箱里 `task` 不可用(工具列表里没有),模型会报错或停下让你开 `/workflow`;`WORKFLOW_TOOLS_NOTE` 只在 `has_workflow_only` 为真时才出现
- 每次会话 workflow 状态独立;`always_workflow = true` 才是全局默认

一句话:`/workflow` 是闸门(人/配置来开),自然语言是闸门打开后让模型编排子代理的方式。

> 追加于 2026-09-02 21:11(completed task 清理策略,接续第 7 节)

### 6. 完成的 task 会清理吗,多久清理

无定时/TTL 清理,全是事件驱动,分三层:

| 层 | 清理时机 |
|---|---|
| 运行态(内存/cancel 槽位) | 立即(任务结束,`SessionState::close()` agent.rs:760-778:retire 取消槽位、flush 转写回父会话、清空自身 history) |
| UI picker(/tasks) | 会话结束 / `/reload`(done/error 后仍保留可查看,运行中排最前;reload 时丢无消息孤儿子代理,tasks.rs 防 pin 个 running forever 的任务) |
| 磁盘(父会话文件) | 无 TTL;仅 rewind 时 `prune_orphans` 清孤儿(sessions.rs:1603-1618);随会话文件归档/shrink 同生共死 |

- `subagent_messages` + `StoredSubagent{tool_use_id, name, model}` 写入父 session 文件长期保留
- 唯一磁盘清理点:rewind 截断主消息后,把不再被主 messages 引用的子代理消息/条目/tool_outputs 清掉(防 ghost 子代理 tab)

结论:当前会话做完随时可在 `/tasks` 翻看;重载后只保留有完整转写的;磁盘一直留到会话归档。

## 八、哪些编码智能体支持工作流任务编排(追加调查)

> 追加于 2026-09-03 05:28

"工作流任务编排" = 把多个子代理/步骤写成可复用脚本(或 DAG)执行,而不是一轮轮对话驱动。按成熟度排序:

### 1. Claude Code —— 最完整(Dynamic Workflows)

2026-05 发布、6 月 GA,最接近标准答案:

- 原理:Claude 按任务现场写 JS 编排脚本,交 `Workflow` 工具后台执行;原语 `agent()`(干净上下文子代理)、`parallel()`(并行屏障)、`pipeline(items, 阶段1, 阶段2...)`(流式过阶段)、`phase()`;脚本内普通 JS 做过滤/去重/循环,不耗 token
- 触发(自然语言可触发):直接说 "use a workflow to…" / "run a workflow";关键词 `ultracode`(`/effort ultracode` 全程自动编排);Agent SDK allow `Workflow` tool + 自然语言请求
- 管理:`/workflows` 列出运行/完成,可暂停恢复(p)、保存为命令(`.claude/workflows/`)或插件分发
- 限制:16 并发 / 1000 agents 每 run;脚本本身不能碰文件系统(只有子代理能);resumable
- 内置示例:`/deep-research`(多源调研 + 对抗验证)

### 2. opencode (sst) —— 内核无,社区插件补

原生只有 `task` 工具(可 background,experimental)。工作流全靠插件:

- mark-hingston/opencode-workflows:Mastra 引擎,JSON/YAML/TS 定义 DAG,agent 可把工作流当工具调,支持并行步骤、条件路由、`suspend` 人工审批、崩溃恢复
- chethann/opencode-tasks:task → research → plan → execute → commit → review → readme 生命周期,`.wip/` 状态门强制前置步骤
- zb-ss/opencode-workflows:手动 supervisor(`/workflow`)+ 自动 DAG(`/workflow-auto`)+ epic(worktree 隔离 + 审查门)+ swarm(并行子会话)

### 3. maki(本项目) —— workflow 模式 = 沙箱脚本编排

workflow 模式下,`code_execution` 沙箱里用 Python 编排:

```python
r1, r2 = await gather(
    task(description="调研前端", prompt="...", subagent_type="research"),
    task(description="调研后端", prompt="...", subagent_type="research"),
)
```

哲学与 Claude Code 一致(计划进代码、中间结果不进上下文),但用 Python 脚本而非 JS;触发靠人 `/workflow`(模型无开关工具)。

### 4. Gemini CLI —— 只有后台任务原语,无脚本编排

`run_shell_command` 的 `is_background`、Ctrl+B/Ctrl+O 后台 shell、`/background` 子命令(A2A 外部 agents,PR 中);无"脚本编排多子代理"的工作流层,官方把长任务做成 skill(async-pr-review)绕。

### 5. Cursor —— 云级并行,非脚本编排

Cloud Agents(隔离 VM 并行)、`/multitask`(异步并行子代理)、计划视图 "Build in Parallel"(按依赖顺序并行执行步骤)。是"并行调度"而非"脚本即编排"。

### 6. Codex CLI / Aider —— 没有

- Codex CLI:子代理仍是 child threads;issue #16900 明说缺显式任务状态/工作流模型,官方搁置(#3968),社区自建被拒
- Aider:`--watch-files` 只是文件注释触发的异步任务,无编排

### 7. 小结

| 智能体 | 脚本化工作流 | 自然语言触发 | 复用/分享 |
|---|---|---|---|
| Claude Code | ✅ JS 脚本(agent/parallel/pipeline) | ✅ 直接说 + `ultracode` 关键词 | ✅ 保存命令/插件 |
| maki | ✅ Python 沙箱脚本 | ❌ 需 `/workflow` 先开 | ⚠️ 手工复用 |
| opencode | ⚠️ 社区插件(DAG/生命周期) | ✅ 插件内 | ✅ 插件 |
| Gemini CLI | ❌(仅后台任务) | — | — |
| Cursor | ❌(并行调度非脚本) | ✅ | ✅ Cloud Agents |
| Codex CLI | ❌ | — | — |
| Aider | ❌ | — | — |

## 九、Claude Code 细节特性领先优势(追加调查)

> 追加于 2026-09-03 07:41

### 1. 多代理编排(深度领先)

四种可组合的编排模式,别家最多一两种:

| 模式 | 语义 |
|---|---|
| Subagents | 会话内委派,独立上下文/模型/工具/权限 |
| Agent Teams(实验) | 多完整 Claude 实例做团队成员,直接互发消息、共享任务列表、任务依赖图;lead 调度、teammates 自协调 |
| Cross-session messaging | 跨本机/跨机器/跨云端 session 传消息;ListAgents+SendMessage 工具;teammate 不能代审批防绕过 |
| Dynamic Workflows | 模型现场写 JS 脚本(agent/parallel/pipeline/phase),后台执行,计划进代码不进上下文,可保存复用/插件分发 |

关键细节:
- Agent Teams 用 JSON 文件信箱(~/.claude/teams/{team}/inboxes/)通信;自动投递 + 空闲通知 + 依赖自动解锁
- Dynamic Workflows:16 并发 / 1000 agents 上限;runtime 隔离(脚本不能碰 FS,只有子代理能);resumable、可暂停/恢复/保存
- `ultracode` 关键词 / `/effort ultracode`:模型自动决定是否用 workflow 编排
- `/batch` 技能:一次大改动拆 5-30 个 worktree 隔离子代理,各开 PR

对比:opencode 只有 task 工具 + 社区插件(DAG);Gemini/Cursor 只有后台子代理;Codex 子代理仍 child threads 无编排。

### 2. 会话管理(细节领先)

- `/rewind`(Esc+Esc):回到历史任意节点,可 restore code+conversation 或只 restore conversation(别家多数无)
- `/branch` 会话树形分支;`/compact [指令]` 定向摘要;`/clear` 保留历史可回来
- 冷会话恢复提示缓存过期:可选"从摘要恢复"(省 token)或"全量恢复"(保细节)
- 跨项目 `--resume <id>`:整机器搜 transcript,不限启动目录

### 3. Worktree 隔离(深度领先)

- 每 session 独立 git worktree(自动创建/清理);子代理可各自隔离(`isolation: worktree` 或口头指定)
- `.worktreeinclude` 自动拷贝 .env 等 untracked 文件;sweep 按 cleanupPeriodDays 清理,期间 git worktree lock 防误删
- 支持非 git VCS(WorktreeCreate/WorktreeRemove hook);resume 自动回 worktree,ExitWorktree 工具退出

### 4. 权限模型(独特)

- 6 档权限模式(别家 2-4 档):plan / default / acceptEdits / dontAsk / bypassPermissions / **auto(classifier 分类驱动)**
- `auto` 模式独有:模型分类器自动决定每次工具调用是否要问
- background 子代理自动拒绝未预批操作但不阻塞运行

### 5. 上下文压缩(compaction)细节领先

- 压缩后重新注入 CLAUDE.md、auto memory、plan;重读最近修改 5 个文件;skill body per-skill 5k / 总 25k 上限
- 压缩请求继承当前 thinking 配置(思考模式压缩更聪明);`/autocompact <token>` 自定义阈值

### 6. 生态系统壁垒

- SKILL.md 约定 Anthropic 首创,现被 Copilot/OpenCode 采纳(标准制定者)
- 2810+ skills / 425 plugins / 200 agents 市场规模;MCP 参考实现
- 100 万 token 上下文(与 Gemini 并列最大);SWE-bench Verified 80.9%

### 7. 非交互/CI

- `claude -p` + `--permission-mode` + `--output-format json|stream-json`(事件流可 tee 到日志)
- Agent SDK(Python/TS)可触发 workflow;GitHub Actions / GitLab CI 官方集成;`--from-pr` 从 PR 恢复

### 8. 短板(客观)

- 无 OS 级沙箱(Docker/Seatbelt/Landlock)——Gemini、Codex 领先
- 模型锁定(仅 Anthropic);本地模型不支持;成本最高(Opus 单会话 $0.5-2.25)
